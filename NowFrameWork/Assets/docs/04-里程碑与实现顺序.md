# 04 里程碑与实现顺序

> 上游：[03-模块清单与优先级](03-模块清单与优先级.md) ｜ 下游：[05-技术方案-Addressables与HybridCLR](05-技术方案-Addressables与HybridCLR.md)

## 1. 排序原则

1. **先打通最危险的链路**。Addressables × HybridCLR × IL2CPP 裁剪是唯一"不做出来就无法承诺架构"的部分，且会反向决定程序集划分（AOT/热更边界、程序集数量、裁剪策略）。放在 M0，失败也能在 2 人日内切换方案。
2. **内核先于表现**。没有容器/事件/日志/时间，资源与 UI 写出来也是临时的。
3. **表现层按依赖顺序**：资源 → 流程 → UI。反过来做必然重写。
4. **玩法能力最后**。框架抽象必须由真实垂直切片检验，先做玩法等于用业务猜框架。
5. **测试与工具随阶段生长**，不设"专门的测试阶段"——那通常不会发生。
6. **每个里程碑必须有可运行的产物**，不接受"只有接口和空实现"的阶段。

| 里程碑 | 主题 | 交付模块 | 估算（人日） | 关键退出标准 |
|---|---|---|---|---|

| M3 | UI·表现·存档 | C11、F04–F09 | 21–27 | 3 界面闭环、手柄可完整操作、存档迁移通过 |
| M4 | 热更与出包流水线 | F02 完整、T02 完整、T03 骨架 | 9–12 | 一条命令出包 + 补丁 + 可回滚 |

**合计 90–125 人日**（v0.3 重估；不含主机迁移的 5–8 人日）。其中**框架本体（M0–M4）= 71–92 人日**，**M5 Gameplay 示例 = 20–30 人日且不计入框架交付**（[ADR-021](07-架构决策记录ADR.md)）。估算不含业务内容、美术、主机认证。置信度：M0/M1 中高（±25%），M2/M3 中（±30%），M5 低（±50%，取决于玩法复杂度）。

**v0.3 重估说明**：原表按"模块主干跑通"计，现按"模块含接口、实现、单测、日志、失败路径与联调"计。主要上调：T1.1（5→7）、T2.1（6→8）、T2.4（4→6.5）、T3.1（6→8）、T4.1+T4.2（7→9）；下调：M0 因撤销双引擎验证减 1–2 天。

## 3. M0 技术预研（9–11 人日）

目标：用最小代价证伪或证实"Addressables + HybridCLR + IL2CPP"这条链路在**团结 1.8.2** 上可用。

**前置 2 小时**：先只做一件事——装 HybridCLR，看它的安装器认不认 `2022.3.62t4` 这个 `t` 版本、`Generate/All` 能否跑完。不认就先换 `v8.15.0` 再试；两个都不行，M0 立刻停下来评估方案，不要继续往下写脚本。

### 3.1 任务分解

| 编号 | 任务 | 产出 | 预估 |
|---|---|---|---|
| T0.1 | 工程基线：用**团结引擎 1.8.2**（2022.3.62t4）新建工程，目录与 asmdef 骨架、`.editorconfig`、Git 忽略与 LFS、安装 Addressables 1.22.4-t1 / HybridCLR（锁 tag）/ UniTask（锁 commit）/ Input System | 可编译空工程 | 1.5 |
| T0.2 | Addressables 最小闭环：本地组 + 远端组、catalog 更新、增量构建、加载一个 Prefab 与一个场景 | 远端更新 demo | 2 |
| T0.3 | HybridCLR 最小热更：`HotUpdateAssemblies` 配置、`Generate/All`、dll 入组、`LoadMetadataForAOTAssembly`、`Assembly.Load`、入口调用 | 热更 demo | 3 |
| T0.4 | IL2CPP 裁剪验证：`Api Compatibility = .NET Framework`、`Managed Stripping = Minimal`、link.xml、`AOTGenericReferences`、故意制造一次 AOT 泛型缺失并定位 | 裁剪结论 + 修复清单 | 1.5 |
| T0.5 | 构建脚本原型：`-batchmode -executeMethod BuildTools.BuildWin64`，`-EnginePath` 参数化（默认 `Tuanjie.exe`，为将来迁移留口），产物目录与版本号写入 | 可重复执行的出包脚本 | 1 |
| T0.6 | 结论报告：锁定版本矩阵（含团结 1.8.2 与 HybridCLR/UniTask 的具体 tag）、问题清单、是否继续 Addressables 的判定 | 报告 + 更新 [README](README.md) 第 8 节 | 1 |

### 3.2 退出标准（逐条演示）

- [ ] Win64 IL2CPP 包启动 → Addressables 加载场景与 Prefab → 从组内加载热更 dll → UGUI 显示由热更代码生成的文字；
- [ ] 只改热更层一行代码 → 重出补丁 → 不重装客户端即生效；
- [ ] HybridCLR 安装器能识别团结 1.8.2（`2022.3.62t4`）并完成 `Generate/All`，所用 tag 与产物路径记录在案；
- [ ] Player 包内**确认不含**热更程序集（`Game.Logic` 的 AOT 副本），不能只信"构建钩子自动排除"；
- [ ] 故意删除一个 AOT 泛型元数据 → 能复现并定位到具体类型（证明排查手段可用）；
- [ ] 出包脚本连续执行两次，产物一致、可追溯版本号。

### 3.3 失败出口

若 M0 中 Addressables 出现无法在 2 人日内解决的阻塞（典型：catalog 与 dll 分组的循环依赖、远端更新与 IL2CPP 裁剪冲突、增量构建不可靠），**立即切换 YooAsset**：

- 切换成本预估 ≤ 2 人日（F01 的接口不变，只换 Provider 实现）；
- 切换后重新验证 T0.3/T0.4，M0 顺延不超过 3 人日；
- 决策记入 [07 ADR-004](07-架构决策记录ADR.md)。

## 12. 阶段 DoD

模块级（每个模块完成必须全勾）：

- [ ] 接口在所属层 `Abstractions` 下，实现不暴露内部类型；
- [ ] EditMode 测试覆盖主路径 + 边界（空、越界、重复、失败）；
- [ ] 日志有明确 Tag 与错误上下文；
- [ ] 无静态可变状态（容器持有的一次性引用除外）；
- [ ] 无每帧分配；Profiler 无新增 GC；
- [ ] 在 [03](03-模块清单与优先级.md) 的验收要点全部通过；
- [ ] 文档段落与示例（Samples 或测试用例）就位。

里程碑级：

- [ ] 退出标准逐条演示并留证据（录屏/日志/构建报告）；
- [ ] 单测与冒烟全绿；
- [ ] 文档与 ADR 更新；
- [ ] 版本矩阵未漂移（如有升级，补一次 M4 冒烟）。

## 13. 变更管理

- 里程碑内允许 ±20% 的任务增删；超出或影响退出标准，必须走一次 ADR 评审。
- M0 的结论可以**否定**后续计划：例如 Addressables 换成 YooAsset，则 F01 实现替换、[05](05-技术方案-Addressables与HybridCLR.md) 第 1 节重写，但接口与 M1–M4 排期不变。
- 任何"先跳过测试/先跳过文档"的提议，一律按未完成处理。
