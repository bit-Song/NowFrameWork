# 01 目标与范围

> 上游：[README](README.md) ｜ 下游：[02-架构分层与依赖规则](02-架构分层与依赖规则.md)

## 1. 定位

**NowFrameWork** 服务于**中大型单机项目**：PC（Steam 等）为第一平台，主机（PS5 / Xbox Series）后置接入。它解决的是"每个项目都要重写一遍"的工程底座问题——启动流程、模块组织、资源与场景、UI、存档、设置、输入、构建与热更——而不是替项目决定玩法。

一句话：**框架提供"怎么跑起来"，项目决定"跑什么"。**

## 2. 目标

| 编号 | 目标 | 可验证结果 |
|---|---|---|
| G1 | 可复用 | 新工程接入 ≤ 1 人日：引 UPM 包 + Boot 场景 + 首个界面 |
| G2 | 可裁剪 | 39 个模块按 P0/P1/P2 分级，P1/P2 不引入时不产生编译与运行时成本 |
| G3 | 可验证 | 每个 P0 模块有 EditMode 测试；每个里程碑有可运行的退出标准 |

框架自身的三个设计取向：

- **业务不碰底层 API**：业务只接触 `IAssetService` / `IUIService` / `IFlowService` 等接口，Addressables、HybridCLR、Input System 的 API 一律封装在框架内部。
- **单向依赖**：AOT 不引用热更，上层不反向依赖下层，业务不依赖框架实现类。
- **默认安全**：所有异步可取消、所有外部数据可校验、所有版本可回退。

## 3. 非目标（明确不做）

| 不做 | 原因 | 替代 |
|---|---|---|
| DOTS / ECS 全量重构 | 单机项目收益不确定，学习与迁移成本高 | Gameplay 层可选局部使用 |
| 联网同步 / 服务端框架 | 单机定位 | F12 只留 HTTP 能力，不建长连接层 |
| 可视化脚本 / 技能编辑器 | 属于项目工具，不是通用底座 | G02 只提供运行时，编辑器后置 |
| 多引擎抽象 / 自研渲染管线 | 只服务 Unity | — |
| 主机认证全量合规（奖杯/家长控制/存档规范） | 依赖具体平台与发行方 | M4 起按平台单独立项 |
| 商业化/支付/统计 SDK 封装 | 项目差异过大 | 通过 C12 `IPlatform` 适配 |
| 2D 与 3D 两套 Gameplay 实现 | 维度由接入方项目决定，框架不该替项目选 | Gameplay 只交付接口 + `Samples~` 里的 3D 参考实现，2D 由项目按接口自写（ADR-021） |

## 4. 质量属性与预算

初始预算，M2/M3 后按真实项目校准；一旦校准，写入 [06](06-工程规范-测试与验收.md) 的回归基线。

| 指标 | 目标 | 测量方式 | 校验里程碑 |
|---|---|---|---|
| 冷启动到首帧 | ≤ 1.5 s | 启动埋点（`PerfScope`） | M2 |
| 启动到主菜单可交互（无补丁下载） | ≤ 5 s | 启动埋点 | M2 |
| 场景切换（同质量档，含 Loading） | ≤ 3 s | 埋点 | M3 |
| 框架层稳态 GC Alloc | 0 B/帧 | Profiler（Development Build） | M1 起持续 |
| 框架层单帧 CPU 开销 | ≤ 1.0 ms | Profiler | M3 |
| 空项目常驻托管内存 | ≤ 150 MB | Memory Profiler | M2 |
| UI 打开（已缓存） | ≤ 50 ms | 埋点 | M3 |
| UI 首开（含资源加载） | ≤ 200 ms | 埋点 | M3 |
| 热更补丁体积（首版） | ≤ 20 MB | 构建报告 | M4 |
| 框架代码体积（Core + Foundation dll） | ≤ 3 MB | 构建报告 | M4 |
| 单次出包耗时（Win64 IL2CPP，增量） | ≤ 15 min | CI 计时 | M4 |

质量属性优先级：**稳定性 > 可维护性 > 性能 > 包体**。冲突时按此顺序取舍。

## 5. 平台矩阵

> 引擎基线：**团结引擎 1.8.2（底层 2022.3.62t4）为唯一开发与出包环境**。Unity 2022.3.67f2 不再作为兼容验证环境，只是"主机立项后整体迁移"的目标（ADR-017 v0.3）。

| 平台 | 状态 | 说明 |
|---|---|---|
| Windows x64 | **首要验证平台** | M0 起全程在团结 1.8.2 上验证与出包；不要求 Unity 侧能打开本工程 |
| macOS（Apple Silicon） | 可选 | IL2CPP 通用链路，M4 抽检 |
| 小游戏（微信 / 抖音） | 条件扩展 | 团结独有优势；框架按需移植，不计入首版承诺 |
| OpenHarmony / 车机（HMI Android） | 条件扩展 | 团结独有；同样按需，不进首版 |
| PlayStation 5 / Xbox Series | **条件项** | 团结未提供这些构建目标；一旦立项需**整体迁移**到 Unity 2022.3.67f2（GUID/场景格式转换 + 重烘 + 重打 AB，预估 5–8 人日），业务 C# 代码不变（ADR-017） |
| Nintendo Switch | 不纳入 | 内存、HybridCLR 与合规均需单独验证 |

**渲染形态**：2D 与 3D 都必须能接入，但框架本体**不含任何维度实现**——Core / Foundation 不得引用 `Physics`、`Physics2D`、`Renderer`、`SpriteRenderer` 与任何渲染管线命名空间；Gameplay 只提供接口和 `Samples~` 里的一套 3D 参考实现，2D 项目按同一套接口自行实现（ADR-021）。验证方式见第 7 节的 2D 空工程接入。

平台差异统一收敛到 C12 `IPlatform`，业务层不得出现 `#if UNITY_STANDALONE` 之类的平台分支；引擎差异只允许出现在构建脚本与 `IPlatform` 实现中（迁移时另计）。

## 6. 关键约束

1. **AOT 程序集不得引用热更程序集**——HybridCLR 打包会报错（[官方说明](https://www.hybridclr.cn/docs/8.15.0/basic/hotupdateassemblysetting)）。
2. **热更层不得包含框架代码**——框架必须在 AOT，否则补丁无法修复框架自身。
3. **主机不允许动态加载代码**——若立项主机，版本把同一份业务代码编译进包，走 AOT 入口（ADR-006）；团结引擎当前不提供主机构建目标（ADR-017）。
4. **2022.3 无原生 `Awaitable`**——异步统一 UniTask（ADR-003）。
5. **包内必须自带兜底热更 dll**——补丁损坏时仍能启动（ADR-007）。
6. **引擎基线固定为团结 1.8.2（2022.3 LTS 分支）单环境**——框架层不引入团结独有包（`cn.tuanjie.*`）。这条不是为了双引擎兼容，而是为将来迁移冻结成本；引擎差异只允许出现在构建脚本与 `IPlatform` 实现中（ADR-017）。
7. **资源层锁定 Addressables 1.22.4-t1**（团结 t 版，等同 1.22.3 线）——不采用裸 AB 自研层；升级按大版本发布处理，升级后旧 content state 作废（ADR-018、ADR-019）。

## 7. 成功标准

框架"可用"的判定（M4 结束时逐条验收）：

- [ ] 新工程接入 ≤ 1 人日，流程写入 06 的接入指南；
- [ ] 新增一个 UI 界面 ≤ 0.5 人日（继承 `UIView` + 注册地址）；
- [ ] 新增一张配置表 ≤ 0.5 人日（加表 → 导出 → 生成强类型）；
- [ ] 出一次热更补丁 ≤ 30 分钟（含校验与上传）；
- [ ] P0 模块测试覆盖率：Core ≥ 80%，Foundation ≥ 60%（行覆盖）；
- [ ] Win64 IL2CPP 包连续启动 50 次无失败、无资源泄漏告警；
- [ ] 单环境可复现：干净检出（删 `Library`）在团结 1.8.2 下可编译、可出 Win64 IL2CPP 包，换机器同样成立；
- [ ] 维度中立：T01 检查通过——Core / Foundation 无 `Physics`、`Physics2D`、`Renderer`、管线命名空间引用；
- [ ] 2D 接入验证：用团结 `Universal 2D` 模板新建空工程，按 [06 第 9 节](06-工程规范-测试与验收.md) 跑通「启动 → Loading → 首个界面」，**不改框架一行代码**；
- [ ] 主机 AOT 入口编译通过——仅在主机立项并完成工程迁移后验收，否则跳过（ADR-017）。

本套文档"可用"的判定：

- [ ] 39 个模块均有职责、契约、依赖、优先级、验收要点；
- [ ] 每个里程碑退出标准可运行、可判定；
- [ ] 每个风险项都有验证里程碑与触发后预案；
- [ ] 全局术语、编号、版本矩阵一致。

## 8. 术语

| 术语 | 含义 |
|---|---|
| AOT 层 | 随包编译的程序集，HybridCLR 下不可热更 |
| 热更层 | 运行时通过 `Assembly.Load` 加载的程序集，PC 可热更 |
| P0 / P1 / P2 | 骨架必备 / 通用能力 / 按项目取用 |
| 垂直切片 | 一条从启动到玩法闭环的最小可玩链路，用于验证框架假设 |
| 兜底 dll | 首包内置的热更程序集副本，补丁异常时回退 |
| Addressables 组 | 资源打包与分发单元，决定包体边界与更新粒度 |
| 变体（Variant） | 同资源的多套实现（画质档/语言），运行期选择 |
| DoD | Definition of Done，见 [06](06-工程规范-测试与验收.md) 第 8 节 |

## 9. 假设

1. 团队规模 1–3 名程序，框架与业务并行推进。
2. 允许引入 Addressables、HybridCLR、UniTask 三个第三方依赖，其余尽量自研（ADR-001）。
3. 项目为单机，暂不需要联网对战与服务器权威逻辑。
4. **唯一开发环境为团结引擎 1.8.2**；Unity 2022.3.67f2 只在主机立项时作为迁移目标（预估 5–8 人日）；主机是否立项尚未确定（ADR-017）。
5. 若后续要发小游戏/鸿蒙，优先在业务层适配，不反向污染框架层。
6. 美术与策划工作流（DCC、表格工具）不在本框架范围，只定义接口与规范。
7. 本项目只交付框架、不做业务：2D 与 3D 项目各自在 Gameplay / 业务层实现相机、物理与关卡，框架本体不为任何一种维度提供实现（ADR-021）。
